# CLAUDE.md — gopro-yt-uploader

Desktop app that batch-uploads GoPro videos to YouTube with every per-video setting filled in. The UI text is Traditional Chinese; keep it so. Built and used on Windows; Mac and Linux builds exist (2026-11) but nobody has run them on a real machine, only CI tests. Keep README's 「支援的系統」 honest about that.

Read first when picking this up:
- `README.md` — user-facing setup (Google Cloud OAuth) and usage
- `CLAUDE.local.md` and `docs/HISTORY.md` — personal notes and the project diary; gitignored, so they exist only on the maintainer's machine. Anything personal (accounts, local paths, trips, channel details, real video IDs or titles) goes there, never in committed files, commit messages or test data — this repo is public.

## Commands (Windows, run from this folder)

```powershell
.\.venv\Scripts\python.exe -m pytest -q                  # tests; build fake GoPro MP4s, no network
.\.venv\Scripts\python.exe -m gopro_uploader --debug     # open the window with devtools
.\run.bat                                                # dev launcher from source (creates .venv on first run)
.\build.bat                                              # PyInstaller → dist\GoProYTUploader\GoProYTUploader.exe
```

- Pushing a tag `v*` runs `.github/workflows/release.yml`: on Windows, macOS (arm64) and Ubuntu runners each tests, `packaging/build.py`, zips; then one Release with whatever built.
- The real deliverable for users is the PyInstaller build (onedir, `--windowed`; a `.app` on Mac), not `run.bat`. `packaging/build.py` (called by `build.bat`) deletes every googleapiclient discovery doc except `youtube.v3.json` (saves ~100 MB). Icon is generated by `packaging/make_icon.py` (blue upload arrow; don't make it look like YouTube's logo); only Windows gets it (a Mac `.icns` needs Pillow). PyInstaller can't cross-compile.
- OS-specific code: `taskbar.py` is Windows-only and a no-op elsewhere; `app.reveal_command` / `open_with_default_app` use Explorer / `os.startfile`, `open -R` / `open`, `xdg-open`; the close question is a Win32 MessageBox, else pywebview's confirmation dialog; app data is `%APPDATA%`, `~/Library/Application Support`, or `$XDG_DATA_HOME` / `~/.local/share`. Linux gets pywebview's Qt backend from pip (`pywebview[qt]`).
- `.venv` is Python 3.10 (google-api-core warns 3.10 is unsupported; works, upgrade later).
- No system ffmpeg/ffprobe/exiftool. Metadata is parsed in pure Python. Chapter merging uses the ffmpeg binary bundled in the `imageio-ffmpeg` pip package.
- Set `GOPRO_YT_HOME=<dir>` to redirect app data (settings, OAuth token, state, logs) away from the default app data folder. Tests do this automatically.

## Architecture (`gopro_uploader/`)

| Module | Role |
|---|---|
| `mp4meta.py` | MP4 box parser: `mvhd` camera time and duration; GoPro `gpmd` track → GPMF KLV → GPS5 / GPS9 fixes + UTC. Samples are read with a stride to keep HDD seeks low. |
| `scanner.py` | Walks the folder, skips `.LRV`/`.THM`/`_merged`, groups chapters (`GX01xxxx`, `GX02xxxx`… / `GOPRxxxx` + `GPxxxxxx`) into a `Recording`. |
| `planner.py` | `build_plan(recs, settings, overrides, store_lookup, place_lookup)` → list of item dicts for the UI. Owns the time logic (below), nearby-location inference, titles, descriptions, dedupe. Items are always re-derived; user edits live in `overrides`. |
| `geocode.py` | OSM Nominatim reverse/search: 1 req/s, UA header, disk cache of **raw** results (formatting happens on read). `format_place` → `範例寺, 範例区, 範例市`. |
| `youtube.py` | OAuth (InstalledAppFlow, scope `youtube`), `list_playlists` / `create_playlist`, `fetch_videos` (read back), resumable `videos.insert` with retry/backoff, `QuotaExceeded`, fallback without `paidProductPlacementDetails` on HTTP 400. Uploads go into the playlist **picked in the app by id** (`settings.playlist_id`, or `no_playlist`); nothing is ever created from a typed name. |
| `merge.py` | ffmpeg concat demuxer, `-c copy`, maps only v:0 / a:0, writes to `<src>/_merged/` or, when that folder can't be written (a drive from another PC), to `merged/` in app data; checks free space. |
| `store.py` | `state.json` (keyed by first filename + total size; status pending/partial/uploaded/error + video_ids), `upload_history.csv`, per-run log file. |
| `preview.py` | 127.0.0.1 HTTP server (Range support) for the preview player. Serves only registered files under random keys. `lrv_path()` finds GoPro's `.LRV` proxy (`GX010827.MP4` → `GL010827.LRV`), which is H.264; the MP4s are usually HEVC, which WebView2 may not play. |
| `taskbar.py` | ITaskbarList4 via ctypes: progress / error state / flash on the app's own window (matched by process id, so tests never drive a running app). |
| `app.py` | pywebview `Api` class (JS bridge), upload worker thread, events pushed to JS via `window.onEvent`. |
| `ui/index.html` | Single-file vanilla JS UI + Leaflet 1.9.4 (unpkg) with OSM tiles. CARTO tiles now need an API key; don't switch back. |

### Time logic (the subtle part)
- Neither `mvhd.creation_time` nor the file mtime carries a zone. On the HERO tested so far, **mvhd is UTC** (GPS agrees, offset 0) and **mtime is the camera's local clock at the end of recording**. `planner.file_offset()` = (mtime − duration) − mvhd, rounded to 15 min, from the first chapter only → the zone the camera was set to (it changes when the camera's zone is changed on a trip). This is an inference from the data pattern, not a documented GoPro behaviour; it fails if mtimes were rewritten (then `trip_tz` is the fallback).
- Per recording: zone = user's pick (`tz` edit) > file offset mapped to `home_tz`/`trip_tz` > `trip_tz`. UTC = GPS > mvhd as UTC when a file offset exists > older camera-clock logic. `local_time` edits are read in the recording's zone.
- Title = local time in that zone with `title_format`, plus the zone abbreviation (" JST") only when the offset differs from `home_tz` (default `Asia/Taipei`; home times stay unlabeled).
- A camera with a reset clock writes the same mvhd into every clip. Those get `time_suspect`; `_guess_dates` gives them the date of the nearest good recordings before/after **by GoPro file number** (both differ → later day + `date_uncertain`). Their time is unknown (`time_known=False`): the title is the date alone (`date_part(title_format)`, no zone label). YouTube only stores the date, so a time is only needed for the title; the user fills one in when a clock is visible in the video.
- `local_time` edits are `YYYY-MM-DDTHH:MM` or date-only `YYYY-MM-DD`. The UI uses a date field + a 24-hour text field (the native datetime picker showed 上午/下午 and caused AM/PM mistakes).
- `recording_date` is sent as local date at `T00:00:00Z`, so the day shown in Studio never shifts.
- User edits (title, local_time, tz, place, lat/lon — not the upload tick) persist in `edits.json`, keyed like `state.json`.

### YouTube fields sent per video
Title, description, `categoryId=19`, `defaultLanguage` / `defaultAudioLanguage` (`zh-TW` = Studio's 「中文（台灣）」), `privacyStatus=unlisted`, `selfDeclaredMadeForKids=false`, `containsSyntheticMedia=false`, `paidProductPlacementDetails.hasPaidProductPlacement=false`, `recordingDetails.recordingDate`, `notifySubscribers=false`, then a `playlistItems.insert`.

Verified on real uploads (2026-10): unlisted is **not** forced to private; kids / paid promotion / category / recordingDate / languages stick. **No location is sent**: `recordingDetails.location` / `locationDescription` are deprecated since 2017-06-01 and ignored on both insert and update (Google: "Won't Fix", issuetracker 268030207; tested both). Reading a location set in Studio still works. The app's place name is only a reference with a copy button for pasting into Studio's 「影片地點」 search (that search does **not** accept coordinates; coordinates are only used to look up the name). Don't add API location writes or Studio browser automation unless asked.

YouTube takes each upload at only ~3.5 MB/s (measured 2026-10; network, disk and httplib2 are all 10×+ faster), so `_upload_all` runs `settings.parallel_uploads` (default 3, 1–8) at once in a thread pool, each with its own service object (`youtube.service_copy`; httplib2 is not thread-safe). Order is kept because Studio's content list is sorted by upload date: sessions open in table order (each waits for the previous one's `started` event), each upload holds its last 32 MB chunk until the previous recording is finished (`before_last` hook; while waiting it is "parked" in `_parked` and does not count against the width, up to `MAX_PARKED` extra), and playlist adds wait in state.json `playlist_add` until every earlier file (by name) has left the queue (`_flush_playlist`, also run at batch start); each is inserted at its place by table order (`_add_in_place`, before the first video of this folder that comes after it), not appended, since the playlist may already hold later videos. A failed recording (after the 10 retries, or a local error such as merging) pauses the batch: the running ones before it finish, the ones after it are stopped (`_cut`; the failed one never sets its `done`, so the next can't slip its last chunk through) and resume next time, so it can be redone before later ones finish. On a quota stop (`uploadLimitExceeded`: the channel's daily upload limit, seen after ~80 uploads in a day; the number isn't published; or HTTP 429 `rateLimitExceeded` whose message says "Video Uploads per day": the Cloud project's daily cap, seen after 88; other 429s are retried) the stopped recording goes back to the front of the queue, the running ones finish, and the batch waits, trying again every `QUOTA_PROBE` (1 h) until `quota_reset()` (Pacific midnight + 5 min; 30 min retries after that; the channel limit might be a rolling window, not seen yet) and goes on by itself; 停止 / 傳完就停止 end the wait. Stopped / crashed uploads resume: the session URI is saved in state.json `resume` with a hash of path, size, part and body; `youtube.upload(resume_uri=…)` sets googleapiclient's private `_in_error_state` to ask YouTube how much it has; a changed title/description or an expired session (~1 week) starts over. Each finished video logs size, time and average speed.

While uploading, the worker re-reads each queued recording from `self._items` when its turn comes, so edits to queued rows apply. Only the rows being uploaded (`_uploading_ids`) are locked. Uploaded rows can be edited (upload first, fix titles later): edits to title / description / time / zone are kept, marked `yt_dirty` in state.json (shown as 待更新到 YouTube), and sent with `Api.push_to_youtube` → `youtube.update_snippet` (reads the snippet first, changes only title/description, ~50 units each). Before a time change the title is seeded from YouTube's current title so Studio edits survive. The recording date is not pushed (updating recordingDetails might drop a location set in Studio) — the log says to change it in Studio.

Sign-in expiry (7 days while the Cloud app is "testing"): `youtube.SignedOut` (RefreshError / 401, never plain network errors) → `Api._signed_out()` drops the dead token, tells the user once, flips the account button to 「重新登入」; uploads re-open the browser sign-in and retry the current recording; the window re-checks on focus (≤ every 5 min). The browser sign-in is `youtube._browser_sign_in` (run_local_server's parts, polled): while it waits the window shows 重新開啟登入頁 / 取消登入, it ignores stray requests (favicon) and gives up after `SIGN_IN_TIMEOUT` (10 min) with `SignInCancelled`; a closed sign-in tab used to leave the app waiting for ever.

### Compare with YouTube, and 核對
A scan never touches YouTube: the repo is public, and reading someone's channel unasked would alarm them. 「和 YouTube 比對…」 opens a dialog first: since a date (default the folder's earliest known recording date), one playlist, or the whole channel; the target playlist is always read too, for its order. `youtube.read_playlist` reads a page at a time (about 2 quota units per 50; about 10 s per 1,000 videos), can be cancelled keeping what it has, and with `since` stops at the first page older than the date (the uploads playlist runs newest first; a real channel gave identical local results to reading it all, in about a third of the time). Don't use the uploads playlist's `itemCount` as an estimate: it was far below the real count. The last result stays in `channel.json` until 清除上次結果, sign-in or sign-out.

`_attach_channel` marks a row `on_channel` when a read video has the exact byte size of its file (`on_channel_some` when only some chapters match; 1 MB minimum): this finds renamed copies and hand uploads, which `state.json` can't. API uploads have no `fileName`, hand uploads do. Marked rows are skipped by tick-all, can be ticked one by one, and the upload confirm warns. `compare_result` gives the result dialog a row per recording (已上傳 / 部分 / 可能 = same file name but another size / 沒上傳) plus a row per video nothing matched (只在 YouTube; this app's uploads from other folders, known from `state.json`, get their own kind 別的資料夾傳的), sortable by local or playlist order **for display only**: it exists so what the size missed (a merge, an export) can be spotted by eye. Linking such a pair by hand is not built yet. The API has no draft state, and an unfinished upload may not be listed at all.

Hand uploads (a `fileName` + exact size equal to a chapter here, not uploaded by this app) whose whole recording matched and that aren't drafts are adopted by `_adopt_hand` (on scan, compare and after 修正): state.json gets `status=uploaded`, their `video_ids` and `hand=True`, so they behave like this app's uploads (YouTube box, 更新到 YouTube, 核對; the publishedAt-order check skips them, their upload order can't change). A draft = a placeholder title (shared by 3+ private hand uploads; remembered in channel.json `placeholders` so the last few still count) or the bare file name; those rows show 草稿 and wait for 修正. What this app later does to a hand upload is kept in state.json `by_app` (`fixed` = 修正 from a draft, `pushed` = title / description sent), shown as 已上傳・手動→程式修正 / ・程式改過標題, so they can be told from ones filled in in Studio; `_backfill_by_app` filled it in once from the run logs (`by_log`).

Zone from titles (`planner.zone_hints`): a camera left on the home zone abroad, without GPS, gives the home offset in every file, so the file can't tell. A YouTube title "date time [ABBR]" says it: no label = home (this app's own convention), "JST" = the candidate zone called that. Untitled recordings take the nearest titled ones' zone (both sides agree, or the titled ones on the same camera-clock day agree). Precedence: manual tz > title hint > file offset > trip_tz. `title_time_fix` flags uploaded titles whose leading date/time differs from the file (a minute rounded up is fine) as `title_should`; `fix_title_times` rewrites only the leading time and marks it for 更新到 YouTube. Seen in real use: hand-typed titles took the camera's home clock and appended " JST", an hour early; what is visible in the footage agreed with the file's UTC.

修正手動上傳的影片 (`Api.hand_fixes` / `fix_hand_uploads`; from the result dialog, or from the main table: a selected 草稿 row's 「修正到 YouTube…」 opens the same dialog with only those rows, closes it when done, and a title edited there is what gets sent, after which the edit is dropped; a tick means "deal with this row": ticked drafts are never uploaded (`_upload_all` skips `on_channel_draft`), they get a yellow 修正到 YouTube（N 支） next to 開始上傳, and the fix clears their tick): videos the last comparison read that this app didn't upload and whose `fileName` + exact size equal a chapter of a scanned recording. Default-ticked when 3+ of them share a title (YouTube's placeholder: nothing was filled in). Each gets `youtube.apply_settings` with the normal upload body (title as the app would give it, `(n/N)` for a chapter uploaded alone; privacy from settings): it reads the snippet / status first and keeps their other settable fields, and leaves `recordingDetails` alone when the video has a Studio location. Then `playlistItems.insert` at its place by table order (`position`; videos of this folder are ranked by row and chapter, others in the playlist stay put). ~101 units each; a quota stop ends the run, the new titles are saved into `channel.json`, so the next run goes on. Studio's content list stays in the original upload order. Fixed drafts still show 草稿 in Studio (its upload wizard was never finished; the API can't finish it) but play as unlisted; finishing the wizard by hand defaults to 公開 on its last page.

`Api.verify` (核對 button, read-only) reports for the scanned folder: counts, every uploaded video exists and is processed, byte size equals the local file (not for merged), it is in the playlist **it was uploaded for** (name from `upload_history.csv`, not the one picked now), playlist order and `publishedAt` order follow the table, and dead playlist entries. A wrong playlist order offers 排好順序 (`sort_playlist`: sorts this folder's videos among the places they hold, `playlistItems.update` ~50 units a move, others stay put).

## Conventions
- Keep it dependency-light: pure-Python parsing, no ffprobe requirement.
- Never commit `client_secret*.json` or `token*.json` (both are in `.gitignore`; they live in app data anyway).
- Never touch or delete original video files; only `_merged/*` temp files may be deleted.
- Run `pytest` after changing `mp4meta` / `planner`. `tests/fake_gopro.py` can synthesize GPS5 and GPS9 payloads. Test data is made up: no real places, dates, titles or video IDs from anyone's uploads.
