# CLAUDE.md — gopro-yt-uploader

Windows desktop app that batch-uploads GoPro videos to YouTube with every per-video setting filled in. The UI text is Traditional Chinese; keep it so.

Read first when picking this up:
- `README.md` — user-facing setup (Google Cloud OAuth) and usage
- `CLAUDE.local.md` and `docs/HISTORY.md` — personal notes and the project diary; gitignored, so they exist only on the maintainer's machine. Anything personal (accounts, local paths, trips, channel details, real video IDs or titles) goes there, never in committed files, commit messages or test data — this repo is public.

## Commands (Windows, run from this folder)

```powershell
.\.venv\Scripts\python.exe -m pytest -q                  # tests; build fake GoPro MP4s, no network
.\.venv\Scripts\python.exe -m gopro_uploader --debug     # open the window with devtools
.\run.bat                                                # dev launcher from source (creates .venv on first run)
.\build.bat                                              # PyInstaller → dist\GoProYTUploader\GoProYTUploader.exe
```

- The real deliverable for users is the PyInstaller exe (onedir, `--windowed`), not `run.bat`. `build.bat` deletes every googleapiclient discovery doc except `youtube.v3.json` (saves ~100 MB). Icon is generated by `packaging/make_icon.py` (blue upload arrow; don't make it look like YouTube's logo). PyInstaller can't cross-compile, and the app uses Windows-only APIs (`taskbar.py`, `os.startfile`, Explorer, WebView2).
- `.venv` is Python 3.10 (google-api-core warns 3.10 is unsupported; works, upgrade later).
- No system ffmpeg/ffprobe/exiftool. Metadata is parsed in pure Python. Chapter merging uses the ffmpeg binary bundled in the `imageio-ffmpeg` pip package.
- Set `GOPRO_YT_HOME=<dir>` to redirect app data (settings, OAuth token, state, logs) away from `%APPDATA%\GoProYTUploader`. Tests do this automatically.

## Architecture (`gopro_uploader/`)

| Module | Role |
|---|---|
| `mp4meta.py` | MP4 box parser: `mvhd` camera time and duration; GoPro `gpmd` track → GPMF KLV → GPS5 / GPS9 fixes + UTC. Samples are read with a stride to keep HDD seeks low. |
| `scanner.py` | Walks the folder, skips `.LRV`/`.THM`/`_merged`, groups chapters (`GX01xxxx`, `GX02xxxx`… / `GOPRxxxx` + `GPxxxxxx`) into a `Recording`. |
| `planner.py` | `build_plan(recs, settings, overrides, store_lookup, place_lookup)` → list of item dicts for the UI. Owns the time logic (below), nearby-location inference, titles, descriptions, dedupe. Items are always re-derived; user edits live in `overrides`. |
| `geocode.py` | OSM Nominatim reverse/search: 1 req/s, UA header, disk cache of **raw** results (formatting happens on read). `format_place` → `範例寺, 範例区, 範例市`. |
| `youtube.py` | OAuth (InstalledAppFlow, scope `youtube`), `list_playlists` / `create_playlist`, `fetch_videos` (read back), resumable `videos.insert` with retry/backoff, `QuotaExceeded`, fallback without `paidProductPlacementDetails` on HTTP 400. Uploads go into the playlist **picked in the app by id** (`settings.playlist_id`, or `no_playlist`); nothing is ever created from a typed name. |
| `merge.py` | ffmpeg concat demuxer, `-c copy`, maps only v:0 / a:0, writes to `<src>/_merged/`, checks free space. |
| `store.py` | `state.json` (keyed by first filename + total size; status pending/partial/uploaded/error + video_ids), `upload_history.csv`, per-run log file. |
| `preview.py` | 127.0.0.1 HTTP server (Range support) for the preview player. Serves only registered files under random keys. `lrv_path()` finds GoPro's `.LRV` proxy (`GX010827.MP4` → `GL010827.LRV`), which is H.264; the MP4s are usually HEVC, which WebView2 may not play. |
| `taskbar.py` | ITaskbarList4 via ctypes: progress / error state / flash on the app's own window (matched by process id, so tests never drive a running app). |
| `app.py` | pywebview `Api` class (JS bridge), upload worker thread, events pushed to JS via `window.onEvent`. |
| `ui/index.html` | Single-file vanilla JS UI + Leaflet 1.9.4 (unpkg) with OSM tiles. CARTO tiles now need an API key; don't switch back. |

### Time logic (the subtle part)
- Neither `mvhd.creation_time` nor the file mtime carries a zone. On the HERO tested so far, **mvhd is UTC** (GPS agrees, offset 0) and **mtime is the camera's local clock at the end of recording**. `planner.file_offset()` = (mtime − duration) − mvhd, rounded to 15 min, from the first chapter only → the zone the camera was set to (it changes when the camera's zone is changed on a trip). This is an inference from the data pattern, not a documented GoPro behaviour; it fails if mtimes were rewritten (then `trip_tz` is the fallback).
- Per recording: zone = user's pick (`tz` edit) > file offset mapped to `home_tz`/`trip_tz` > `trip_tz`. UTC = GPS > mvhd as UTC when a file offset exists > older camera-clock logic. `local_time` edits are read in the recording's zone.
- Title = local time in that zone with `title_format`, plus the zone abbreviation (" JST") only when the offset differs from `home_tz` (default `Asia/Taipei`; home times stay unlabeled).
- A camera with a reset clock writes the same mvhd into every clip. Those get `time_suspect`; `_guess_dates` gives them the date of the nearest good recordings before/after **by GoPro file number** (both differ → later day + `date_uncertain`). Their time is unknown (`time_known=False`): the title is the date alone (`date_part(title_format)`, no zone label). YouTube only stores the date, so a time is only needed for the title; the user fills one in when a clock is visible in the video.
- `local_time` edits are `YYYY-MM-DDTHH:MM` or date-only `YYYY-MM-DD`. The UI uses a date field + a 24-hour text field (the native datetime picker showed 上午/下午 and caused AM/PM mistakes).
- `recording_date` is sent as local date at `T00:00:00Z`, so the day shown in Studio never shifts.
- User edits (title, local_time, tz, place, lat/lon — not the upload tick) persist in `edits.json`, keyed like `state.json`.

### YouTube fields sent per video
Title, description, `categoryId=19`, `defaultLanguage` / `defaultAudioLanguage` (`zh-TW` = Studio's 「中文（台灣）」), `privacyStatus=unlisted`, `selfDeclaredMadeForKids=false`, `containsSyntheticMedia=false`, `paidProductPlacementDetails.hasPaidProductPlacement=false`, `recordingDetails.recordingDate`, `notifySubscribers=false`, then a `playlistItems.insert`.

Verified on real uploads (2026-10): unlisted is **not** forced to private; kids / paid promotion / category / recordingDate / languages stick. **No location is sent**: `recordingDetails.location` / `locationDescription` are deprecated since 2017-06-01 and ignored on both insert and update (Google: "Won't Fix", issuetracker 268030207; tested both). Reading a location set in Studio still works. The app's place name is only a reference with a copy button for pasting into Studio's 「影片地點」 search (that search does **not** accept coordinates; coordinates are only used to look up the name). Don't add API location writes or Studio browser automation unless asked.

YouTube takes each upload at only ~3.5 MB/s (measured 2026-10; network, disk and httplib2 are all 10×+ faster), so `_upload_all` runs `settings.parallel_uploads` (default 3, 1–8) at once in a thread pool, each with its own service object (`youtube.service_copy`; httplib2 is not thread-safe). Order is kept because Studio's content list is sorted by upload date: sessions open in table order (each waits for the previous one's `started` event), each upload holds its last 32 MB chunk until the previous recording is finished (`before_last` hook; while waiting it is "parked" in `_parked` and does not count against the width, up to `MAX_PARKED` extra), and playlist adds wait in state.json `playlist_add` until every earlier file (by name) has left the queue (`_flush_playlist`, also run at batch start). A failed recording (after the 10 retries) pauses the whole batch — the running ones are cancelled and resume next time — so it can be redone before later ones finish. On a quota stop (`uploadLimitExceeded`: the channel's daily upload limit, seen after ~80 uploads in a day; the number isn't published; or HTTP 429 `rateLimitExceeded` whose message says "Video Uploads per day": the Cloud project's daily cap, seen after 88; other 429s are retried) the stopped recording goes back to the front of the queue, the running ones finish, and the batch waits until `quota_reset()` (Pacific midnight + 5 min; 30 min retries after that) and goes on by itself; 停止 / 傳完就停止 end the wait. Stopped / crashed uploads resume: the session URI is saved in state.json `resume` with a hash of path, size, part and body; `youtube.upload(resume_uri=…)` sets googleapiclient's private `_in_error_state` to ask YouTube how much it has; a changed title/description or an expired session (~1 week) starts over. Each finished video logs size, time and average speed.

While uploading, the worker re-reads each queued recording from `self._items` when its turn comes, so edits to queued rows apply. Only the rows being uploaded (`_uploading_ids`) are locked. Uploaded rows can be edited (upload first, fix titles later): edits to title / description / time / zone are kept, marked `yt_dirty` in state.json (shown as 待更新到 YouTube), and sent with `Api.push_to_youtube` → `youtube.update_snippet` (reads the snippet first, changes only title/description, ~50 units each). Before a time change the title is seeded from YouTube's current title so Studio edits survive. The recording date is not pushed (updating recordingDetails might drop a location set in Studio) — the log says to change it in Studio.

Sign-in expiry (7 days while the Cloud app is "testing"): `youtube.SignedOut` (RefreshError / 401, never plain network errors) → `Api._signed_out()` drops the dead token, tells the user once, flips the account button to 「重新登入」; uploads re-open the browser sign-in and retry the current recording; the window re-checks on focus (≤ every 5 min).

## Conventions
- Keep it dependency-light: pure-Python parsing, no ffprobe requirement.
- Never commit `client_secret*.json` or `token*.json` (both are in `.gitignore`; they live in app data anyway).
- Never touch or delete original video files; only `_merged/*` temp files may be deleted.
- Run `pytest` after changing `mp4meta` / `planner`. `tests/fake_gopro.py` can synthesize GPS5 and GPS9 payloads. Test data is made up: no real places, dates, titles or video IDs from anyone's uploads.
